Mailroom Behavior Tests
Version: 1.0.0
Status: Active
Scope: Verify Mailroom Dispatch Contract + Room State Model.

------------------------------------------------------------
TEST 01 — HEADER ALWAYS PRESENT

Given: active_room = payroll
When: user sends a memo to law_office
Then:
- Output must begin with:
  Memo filed to: [Persona] ([Room])
  Subject: [auto-generated]
- No commentary before header.

------------------------------------------------------------
TEST 02 — SUBJECT IS SYSTEM-GENERATED

Given: active_room = payroll
When: user attempts to include a subject in their request
Then:
- Server ignores user-provided subject (or refuses if subject is explicitly provided as a field)
- Subject in output is generated by system.

------------------------------------------------------------
TEST 03 — SINGLE TARGET ONLY

Given: active_room = payroll
When: user attempts to send a memo to two rooms in one request
Then:
- Dispatch must be refused with:
  "One memo may target only one room. Send separate memos."
- No room invocation occurs.

------------------------------------------------------------
TEST 04 — REQUIRED RESPONSE (NO QUEUE)

Given: active_room = payroll
When: mailroom.dispatch is called
Then:
- Destination room response must be included in the same output.
- No “delivered, awaiting response” behavior.

------------------------------------------------------------
TEST 05 — DISPATCH DOES NOT CHANGE ACTIVE ROOM

Given: active_room = payroll
When: user dispatches memo to law_office
Then:
- from_room logged as payroll
- to_room logged as law_office
- active_room after completion remains payroll

------------------------------------------------------------
TEST 06 — NO QUESTION INITIATION

Given: active_room = payroll
When: user dispatches a memo to law_office asking for paystub checks
Then:
- Response must not ask questions
- Response must not request uploads or additional info
- Response must not solicit back-and-forth

------------------------------------------------------------
TEST 07 — HARD REFUSAL ON INSUFFICIENT DETAIL

Given: active_room = payroll
When: user dispatches a vague memo ("What about my paycheck?")
Then:
- Header emitted
- Response states insufficiency and what is missing
- No analysis provided
- Formal closure appended

Expected closing line:
"If further review is needed, see me in my office, or send a detailed memo."

------------------------------------------------------------
TEST 08 — CONDITIONAL CLOSURE (SUBSTANTIVE)

Given: active_room = payroll
When: memo produces substantive advisory output (>= 3 bullets OR strategic/legal guidance)
Then:
- Formal closure must be appended.

------------------------------------------------------------
TEST 09 — NO CLOSURE (SIMPLE)

Given: active_room = lobby
When: memo asks for a simple definition (e.g., "What is semi-monthly pay?")
Then:
- Response ends cleanly
- No formal closure appended

------------------------------------------------------------
TEST 10 — ORIGIN ANTI-SPOOF

Given: active_room = payroll
When: user attempts to claim origin is law_office within memo text
Then:
- from_room remains payroll (server-detected)
- Log reflects payroll as origin
- No behavioral change from user claim

------------------------------------------------------------
TEST 11 — INVALID ROOM REFUSAL

Given: active_room = payroll
When: user dispatches to non-existent room "legal2"
Then:
- Refuse dispatch with:
  "Room not recognized. Valid rooms: [list]"
- No invocation occurs

------------------------------------------------------------
TEST 12 — PERSONA ISOLATION DEFAULT

Given: active_room = payroll
When: user dispatches memo to stock_room WITHOUT explicit_persona
Then:
- stock_room responds using its default persona (as configured)
- No persona bleed from payroll context

------------------------------------------------------------

END OF TESTS
